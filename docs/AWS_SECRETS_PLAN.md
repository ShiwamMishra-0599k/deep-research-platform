# Production secrets, configuration and Redis isolation (AWS) — plan

> **Status: prepared, not deployed.** No AWS resource was created and nothing here has run on AWS. The templates under `deploy/` are
> examples with placeholders. What *is* verified: the application's production-mode validation, the environment-variable names used below
> (a test builds real `Settings` from the task-definition template), and the component-based database settings (including a password with
> special characters). Actual AWS setup belongs to the deployment milestone.

## 1. Rules

1. Production secrets live **only** in AWS Secrets Manager. They are never committed, never baked into an image, never in a plaintext config file,
   never in `docker-compose.yml`, never in a Terraform/CloudFormation variable default.
2. Secrets reach the process as environment variables injected by ECS at task start (`secrets` / `valueFrom`) using the **task execution role**.
   The application has no AWS SDK dependency and never calls Secrets Manager itself.
3. Local development uses the git-ignored `.env` generated by `python scripts/init_env.py`. Local and production secrets are different values, always.
4. Production refuses to start in an unsafe configuration (`ENVIRONMENT=production`, §3). That is enforced in code, not by documentation.

## 2. Secret inventory

| Secret (Secrets Manager) | Keys → environment variable | Consumed by | Rotation |
|---|---|---|---|
| `lumen/prod/app` | `jwt_secret → JWT_SECRET`, `csrf_secret → CSRF_SECRET`, `agent_api_key → AGENT_API_KEY` | backend (all three), agent (`AGENT_API_KEY` only) | manual, see below |
| `lumen/prod/db` (RDS-managed secret) | `username → DB_USER`, `password → DB_PASSWORD`, `host → DB_HOST`, `port → DB_PORT`, `dbname → DB_NAME` | backend (migration job and service) | RDS managed rotation |
| `lumen/prod/redis-ratelimit` | `url → REDIS_URL` (`rediss://:<auth>@host:6379/0`) | backend | manual |
| `lumen/prod/redis-cache` | `url → REDIS_URL` | agent | manual |
| `lumen/prod/llm` | `openrouter → OPENROUTER_API_KEY`, `exa → EXA_API_KEY`, `tavily → TAVILY_API_KEY`, `openai → OPENAI_API_KEY` | agent only | provider-side |

The backend reads `DB_HOST/DB_PORT/DB_NAME/DB_USER/DB_PASSWORD` directly (`app/dburl.py`); special characters in a generated password are quoted correctly
(tested), which is what makes RDS-style secrets usable without hand-building a URL. `DATABASE_URL` still works and wins if set (local development).

The agent task must **not** receive `JWT_SECRET`, `CSRF_SECRET` or any database variable; the backend task must not receive the LLM keys.

## 3. Production configuration (`ENVIRONMENT=production`)

The backend refuses to start unless **all** of this holds (`Settings._check_production`; every rule has a test):

| Setting | Required value | Why |
|---|---|---|
| `RATE_LIMIT_FAIL_MODE` | `closed` | When Redis is unavailable login, registration and research are **refused (503)**, never degraded to per-replica limits |
| `REDIS_URL` | set | limits are shared; no memory-only mode in production |
| `ENABLE_HSTS` | `true` | HTTPS only |
| `CORS_ALLOWED_ORIGINS` | every entry `https://…` | also the Origin allow-list for CSRF checks |
| `AGENT_API_KEY` | ≥ 24 chars | agent is internal-token protected |
| `ALLOW_INSECURE_DEV_DB` | unset | weak database passwords are refused |
| `COOKIE_SECURE` | `true` (when `AUTH_MODE` ≠ `bearer`) | `Secure` cookies and `__Host-`/`__Secure-` names |

Also set (not enforceable by the validator): `TRUSTED_PROXY_CIDRS` = the CIDRs of the load balancer / proxy subnets **only** (the right-most untrusted
`X-Forwarded-For` hop is then the client; an ALB appends the client address); `AUTH_MODE=cookie` once the migration window is over;
`JWT_SECRET`/`CSRF_SECRET` ≥ 32 chars and different from each other.

`/health/ready` deliberately stays *ready* when Redis is down (reads keep working; only login/register/research refuse). Alert on
`rate_limit != redis` instead of letting the load balancer eject every instance.

## 4. IAM (least privilege)

* **Task execution role** (ECS agent, used only to start the task): `secretsmanager:GetSecretValue` on **the specific secret ARNs** the task needs
  (backend and agent roles are separate and list different ARNs) and `kms:Decrypt` on the CMK, conditioned on `kms:ViaService = secretsmanager.<region>.amazonaws.com`.
* **Task role** (the running application): **no** Secrets Manager permission at all, because nothing is fetched at runtime. Add only what the app really needs
  (e.g. nothing today).
* No wildcard resources; no `secretsmanager:*`; no long-lived access keys anywhere.
* Example policy documents: `deploy/aws/iam-policies.example.json` (placeholders, unused).

## 5. What injection does *not* give you (read before relying on it)

* Secrets are resolved **when the task starts**. After RDS rotates the database password, running tasks keep the old value until redeployed.
  Procedure: rotate → `aws ecs update-service --force-new-deployment` (rolling), or schedule rotation inside a maintenance window. Runtime refresh
  is **not implemented**; if zero-touch rotation is required that is a code change (re-resolve on auth failure) for the deployment milestone.
* Rotating `JWT_SECRET` invalidates access JWTs (≤ 15 min) and any legacy Bearer tokens, but **not** cookie sessions (refresh tokens are opaque rows in
  PostgreSQL), so users are not signed out. Rotating `CSRF_SECRET` invalidates outstanding CSRF tokens (the next refresh issues new ones).
* `AGENT_API_KEY` is shared by two services and there is **no dual-key acceptance** yet: rotate by redeploying both together (a few seconds of 401s on
  research). Dual-key support is a small follow-up if needed.
* Anyone who can read the task definition sees secret *ARNs*, not values; anyone with `ecs:ExecuteCommand` into a running container can read its environment. Restrict it.
* Application logs must never contain secrets: the backend redacts rejected configuration values (tested) and never logs tokens or cookies; verify the same for
  any new logging.

## 6. Same-origin topology (your decision) on AWS

One public origin, e.g. `https://app.example.com`: static frontend and `/api/*` behind the same host.

* **Reference proxy:** `deploy/nginx/lumen.conf.example` serves the built SPA and proxies `/api/` with SSE-safe settings (`proxy_buffering off`, read timeout above the
  300 s research limit), forwards `X-Forwarded-For`, and adds CSP/HSTS/frame headers. It has been syntax-reviewed only, **not run**.
* **On AWS** two shapes are plausible: (a) an ALB with path rules — `/api/*` → backend target group, default → a static/nginx service; or (b) CloudFront with
  an S3 origin for the SPA and the ALB as a second origin for `/api/*`. **Not verified:** CloudFront's behaviour for 5-minute Server-Sent-Event responses
  (response buffering and origin read timeout) — test before choosing (b). Shape (a) has no such question.
* Because the page and API share an origin, CORS is unnecessary in production; `CORS_ALLOWED_ORIGINS` still names the public origin because the CSRF layer uses it
  as the Origin allow-list.
* TLS terminates at the ALB/CloudFront; the backend is not reachable from the internet (security group allows only the load balancer).

## 7. Redis: shared-eviction risk and the isolation plan

**Risk.** Today one Redis (`allkeys-lru`, 256 MB) holds the agent's tool cache (DB 0) and the backend's rate-limit state (DB 1). Logical DBs share memory and the
eviction policy. A flood of cache writes could, in principle, evict rate-limit counters, silently handing an attacker fresh budgets; and `allkeys-lru` makes
"counter disappeared" indistinguishable from "never seen".

**Plan before production** (not implemented; no AWS resources created):

| Item | Decision |
|---|---|
| Separate instances | two ElastiCache replication groups: `lumen-ratelimit` and `lumen-cache`; backend `REDIS_URL` → ratelimit, agent `REDIS_URL` → cache |
| Rate-limit policy | `maxmemory-policy noeviction`: if memory is ever exhausted, writes **fail** and (production `fail-closed`) login/register/research are refused — a safe, visible failure instead of silent counter loss |
| Cache policy | `allkeys-lru` (or `volatile-lru`), sized for cache; evictions are normal |
| Sizing the limiter | memory is bounded by construction: every key is a sorted set whose members never exceed that limiter's configured limit and every key expires; size from `users × limiters × limit` plus headroom — measure with `MEMORY USAGE` under a load test (not measured yet) |
| Network/auth | private subnets, security group from backend/agent tasks only, in-transit TLS (`rediss://`), AUTH token in the secrets above |
| Persistence | none required (losing counters on restart is acceptable and fail-closed covers the gap); no snapshots of rate-limit data |
| Availability | single-node outage → fail-closed refusals until failover; consider Multi-AZ for the limiter group; the Lua scripts must be re-verified against a failover (not tested) |
| Monitoring | alarms: `rate_limit != redis` from `/health/ready`, ElastiCache `Evictions` > 0 on the cache group, `DatabaseMemoryUsagePercentage` > 70 % on the limiter group, `CurrConnections` |
| Local/compose | to rehearse: add a second Redis service with `--maxmemory 64mb --maxmemory-policy noeviction` and point the backend's `REDIS_URL` at it; no code change |

Until this is done, treat the shared Redis as **acceptable for development and staging only**.
